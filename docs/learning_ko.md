# 내가 설명할 수 있어야 할 내용

## 이 프로젝트는 무엇인가?

고객 불만을 읽고 어떤 상품의 지원팀이 적합할지 제안하되, 애매한 사례는 사람에게 남기는 작은 분석 프로젝트다. 핵심은 “모델이 전부 처리해야 할까?”라는 질문이다. 최종 버전은 로컬 분류 모델과 Python 규칙만 사용한다. LLM이나 API 키는 필요 없다.

## 어떤 데이터를 썼나?

미국 CFPB의 공식 과거 공개 불만 자료다. 2024년 1~6월 신용카드, 예금계좌, 주택담보대출, 채권추심에서 작은 표본을 골랐다. 글 길이·간단한 영어 검사·중복 및 유사 글 제거 후 3,192건이 남았다. 전체 고객이나 실제 회사의 불만 분포를 대표하지 않는다.

## 모델은 무엇을 배웠나?

TF-IDF는 단어와 두 단어 조합을 숫자로 바꾼다. Logistic Regression은 표현마다 가중치를 배워 네 상품 중 하나를 고른다. 사람이 읽듯 상황을 이해하거나 피해 정도를 판단하는 것은 아니다. 학습은 1~3월 1,681건, 검토 기준 선택은 4월 489건, 최종 평가는 5~6월 1,022건이다. 정답 라벨·접수 날짜·회사 답변은 입력이 아니다.

## 사람 검토 기준은 무엇인가?

입력이 길이·영어 검사에 맞지 않거나, 1등과 2등 유형 점수 차이가 0.1 미만이면 검토로 남긴다. 예를 들어 0.48과 0.43이면 차이가 0.05이므로 검토한다. 0.48을 “정답 확률 48%”라고 해석하면 안 된다. 개발 데이터에서 고른 기준을 마지막 평가에는 바꾸지 않았다. 실제 회사에 적합한 오류 허용치인지는 별도 판단이 필요하다.

검토가 필요할 때 표시된 유형과 팀은 잠정 후보다. 실제로 팀에 보내거나 고객에게 답장하지 않는다.

## 결과는 무엇인가?

1,022건을 모두 분류하면 공개 라벨과 다른 제안이 140건(13.7%)이었다. 규칙을 쓰면 145건(14.2%)을 사람에게 남기고 877건을 제안했다. 그중 63건(7.2%)이 라벨과 달랐다. 전체 사례 대비 잘못된 제안은 6.2%다.

원래 오류 140건 중 77건(55%)을 사람 검토로 남겼지만, 원래 라벨과 맞던 68건도 검토하게 된다. 검토량이라는 대가가 있다. 사람이 그 사례를 올바르게 고쳤다고 가정하지 않는다.

## 무엇을 입증하지 못했나?

실제 직원의 시간 절약, 비용 절감, 고객 만족 개선, 사람+AI의 우수성은 측정하지 않았다. 공개 상품 라벨도 완벽한 업무 정답이 아니다. 영어 검사·유사 글 제거·범위 밖 입력 판별도 완벽하지 않다. 어떤 기준이 회사에 최적인지는 실제 오류 비용과 검토 인력을 알아야 판단할 수 있다.

## LLM은 어떻게 됐나?

처음에는 작은 도구 사용 에이전트도 경험하려 했지만, 최종 범위에서 제외했다. API 연결 시도 중 실패한 결과는 분류 성과로 세지 않는다. 지금 완성본은 “텍스트 분류 + 사람 검토 규칙” 프로젝트다. 에이전트를 완성하거나 평가했다고 설명하지 않는다. 기존 기록 파일은 실행 이력을 보존하기 위해 남겨 둔다.

## 코드 읽는 순서

1. `protocol.json`: 결과를 보기 전에 고정한 데이터·분할·검토 후보 기준. 과거 선택적 확장을 위한 미사용 필드 하나는 원본 해시 확인을 위해 보존했다.
2. `cra/data.py`: 공식 자료 읽기, 작은 표본 선택, 중복 제거와 날짜 분할.
3. `cra/model.py`: 모델 학습, 유형 예측, 검토 기준 선택과 적용.
4. `cra/evaluate.py`: 자동 제안 범위와 오류를 함께 계산.
5. `cra/cli.py`: 데이터 준비와 학습·평가 명령.
6. `app/streamlit_app.py`: 결과와 직접 입력 예시를 보여주는 화면.

## 내 말로 설명해 볼 것

- 왜 모든 사례를 분류하는 방식과 비교했는가?
- 오류율이 줄었는데도 추가 검토량을 함께 보여줘야 하는 이유는?
- 검토 기준을 높이면 어떤 사례와 업무가 달라질까?
- 잘못 분류하는 비용과 사람이 확인하는 비용 중 무엇이 중요한가?

구현·테스트·초기 문서는 AI 지원을 받았다. 모든 코드를 혼자 썼다고 설명하지 않는다. 직접 예시를 실행하고 코드와 결과를 이해한 부분, 질문과 해석에 내가 판단한 부분을 구분해서 말한다. 앱과 보고서의 reflection은 내 경험과 생각에 맞게 다듬을 초안이다.

공개 수치는 10월 29일 네 Windows 실행을 반영했다. 원래 실행과 정리된 데이터·기준·과거 고정 표본의 해시는 같지만 라이브러리 버전과 예측 일부가 달랐다. 버전 차이는 가능한 설명이지 원인을 분리해 입증한 것은 아니다. 더 유리한 수치를 고른 것이 아니며, 새로운 독립 검증도 아니다.
